<a id="数字一"></a>
# 数字一：工具描述 Token 占用减少约 85%

## ① 测试数据怎么构建

不需要"数据集"，需要的是**一份工具注册表快照**。但快照必须覆盖真实场景，因为
节省率**几乎完全取决于接了多少个 MCP 工具**：

| 场景 | 工具构成 | 会被延迟的工具 | 预期节省率 |
|---|---|---|---|
| A 纯内置 | 6 个文件/命令工具 + ToolSearch + Agent + Team* | `AskUserQuestion`、`EnterWorktree`、`ExitWorktree`（3 个） | 低 |
| B 内置 + 1 个 MCP server | A + context7 的 2 个工具 | A 的 3 个 + 2 个 MCP = 5 个 | 中 |
| **C 内置 + 多个 MCP server** | A + N 个 server 的几十个工具 | **大头在这里** | **高（85% 量级）** |

**构建步骤**：按场景 C 真实启动一次 Agent，把注册表里所有工具的
`get_schema()` 结果导出成 JSON，作为快照文件版本化保存。
下次测用同一份快照，数字才可比。

## ② 数据长什么样

快照里每个工具条目是这个形状（`tools/base.py:40-47` 的 `get_schema()`）：

```json
{
  "name": "mcp_context7_query-docs",
  "description": "Retrieves and queries up-to-date documentation and code examples...",
  "input_schema": {
    "properties": {
      "libraryId": { "type": "string", "description": "..." },
      "query":     { "type": "string", "description": "..." }
    },
    "required": ["libraryId", "query"],
    "type": "object"
  }
}
```

对照组里还有内置工具，它们的 schema 直接内联（`read_file.py:20-23`）：

```json
{
  "name": "ReadFile",
  "description": "Read a file and return its contents with line numbers.",
  "input_schema": {
    "properties": {
      "file_path": { "type": "string", "description": "Absolute or relative path..." },
      "offset":    { "type": "integer", "description": "Line offset to start reading from (0-based)" },
      "limit":     { "type": "integer", "description": "Maximum number of lines to read" }
    },
    "required": ["file_path"],
    "type": "object"
  }
}
```

**每个工具几百到几千字节。** 一个 MCP server 挂 20~30 个工具，就是几万字节。

被延迟的工具不下发 schema，只在 system reminder 里留一行名字：

```
The following deferred tools are available via ToolSearch. Their schemas are NOT
loaded - use ToolSearch with query "select:<name>[,<name>...]" to load tool
schemas before calling them:
AskUserQuestion
EnterWorktree
ExitWorktree
mcp_context7_resolve-library-id
mcp_context7_query-docs
```

**这就是全部机制**：把 `N 个完整 schema` 换成 `N 个名字 + 1 个 ToolSearch 的 schema`。

## ③ 怎么测

```python
import json
from mewcode.tools import create_default_registry

CHARS_PER_TOKEN = 3.5          # 代码库统一启发值，见 conversation.py:43

reg = create_default_registry()
# ...按场景 C 把 MCP / Agent / Team 等真实注册进去...

all_tools = reg.list_tools()

# 前置：全量下发（不延迟）
before_chars = sum(
    len(json.dumps(t.get_schema(), ensure_ascii=False)) for t in all_tools
)

# 后置：只发非延迟工具的 schema + 延迟工具的名字清单
kept_chars = sum(
    len(json.dumps(t.get_schema(), ensure_ascii=False))
    for t in all_tools if not getattr(t, "should_defer", False)
)
names = reg.get_deferred_tool_names()          # tools/__init__.py:50-57
reminder_chars = 220 + sum(len(n) + 1 for n in names)   # 提示语 + 每行一个名字

before = before_chars / CHARS_PER_TOKEN
after = (kept_chars + reminder_chars) / CHARS_PER_TOKEN
```

## ④ 评估指标

| 指标 | 公式 | 方向 |
|---|---|---|
| schema 字节数（前 / 后） | `Σ len(json.dumps(get_schema()))` | ↓ |
| **Token 节省率** | `1 − after / before` | ↑ |
| 延迟工具占比 | `延迟工具字节 / 全部字节` | 参考（解释节省率来源） |
| **按需加载代价** | 为加载工具额外花的 tool call 数 | ↓ |
| **净收益** | `省下的 token × 单价 − 多出的轮次 × 往返延迟` | ↑ |

## ⑤ 从代码反推：当初可能是怎么做的

### 反推依据

**默认被延迟的工具只有 3 个内置的**（全部 `should_defer = True`）：

| 工具 | 位置 |
|---|---|
| `AskUserQuestion` | `tools/ask_user.py:54` |
| `EnterWorktree` | `tools/enter_worktree.py:38` |
| `ExitWorktree` | `tools/exit_worktree.py:41` |
| **所有 MCP 工具** | `mcp/tool_wrapper.py:75`（`MCPToolWrapper` 无条件设 True） |
| `ToolSearch` | `tools/impl/tool_search.py:32` —— **显式设 False，永不延迟**（注释写明） |

排除逻辑在 `tools/__init__.py:124-131`：

```python
def get_all_schemas(self, protocol="anthropic"):
    for name, tool in self._tools.items():
        if name in self._disabled:
            continue
        if getattr(tool, "should_defer", False) and name not in self._discovered:
            continue          # ← 延迟且未被发现 → 不下发 schema
        schemas.append(...)
```

### 由此推出的三条结论

**1. 85% 这个量级只可能来自"接了 MCP server"的场景。**
只有 3 个内置工具被延迟时，节省率顶多 20~35%，到不了 85%。
而 MCP 工具的 schema 是**逐字照抄 MCP server 的 `inputSchema`**
（`mcp/tool_wrapper.py:77,85-90`），真实 MCP server 的 schema 往往非常啰嗦。
所以测的必然是"内置 + N 个 MCP server"的运行态。

**2. 测法几乎肯定就是"机制开/关两种状态下比 schema 字节数"。**

```python
before = Σ len(json.dumps(t.get_schema()))  over 全部工具          # 机制关闭
after  = Σ len(json.dumps(t.get_schema()))  over get_all_schemas()  # 机制开启
       + 延迟工具名字清单的字节数
节省率 = 1 - after / before
```

"机制关闭"的等价操作：把所有工具的 `should_defer` 置 `False`，
或者直接对 `list_tools()` 全量求和。

**3. 分母里必须包含 `ToolSearch` 自己的 schema。** 它是这个机制的**固定成本**，
注释里特意写了"永不延迟加载"。漏掉它算出来的节省率会偏高。

# 数字二：权限弹窗从平均 30 次降至 5 次以内

## ① 测试数据怎么构建

弹窗次数**完全取决于任务构成**——纯读任务 0 次，全写任务几十次。
所以必须构建**固定任务集**并版本化保存：

| 类别 | 每类数量 | 例 | 弹窗密度 |
|---|---|---|---|
| 只读排查 | 5 | "这个函数在哪被调用"、"看下这个报错" | 低 |
| 单文件编辑 | 5 | "给这个函数加参数校验" | 中 |
| 跨文件重构 | 5 | "把这个抽象改名并更新所有引用" | 高 |

**同时需要一份"会话录制"**：一次真实会话的完整工具调用序列。
`.mewcode/sessions/*.jsonl` 本身就是这个格式，直接拿来用。

## ② 数据长什么样

任务集条目：

```json
{
  "task_id": "refactor-003",
  "category": "cross_file",
  "prompt": "把 _relay_catalog_517 这个抽象改名为 _relay_index_517，并更新所有引用",
  "expected_files": 4,
  "expected_tool_calls": 12
}
```

会话录制（就是真实 jsonl 的一行，assistant 发起调用）：

```json
{"type": "assistant",
 "content": [{"type": "tool_use", "id": "call_00_x7f", "name": "EditFile",
              "input": {"file_path": "src/relay.py", "old_string": "...", "new_string": "..."}}],
 "timestamp": "..."}
{"type": "assistant",
 "content": [{"type": "tool_use", "id": "call_01_k2m", "name": "Bash",
              "input": {"command": "pytest -k relay_index -q"}}],
 "timestamp": "..."}
```

**这一对 (tool_name, arguments) 就是重放的输入** —— 对每个调用调一次
`checker.check(tool, arguments)`，看返回是不是 `ask`。

## ③ 怎么测

弹窗的唯一触发点是 `permissions/checker.py` 的 Layer 5。整条流水线是：

```
Layer 0   Plan 模式例外放行（Agent/ToolSearch/AskUserQuestion/ExitPlanMode + plan 文件）
Layer 1   is_safe_command() 只读白名单命中 → allow      ← 不打弹窗
Layer 1b  DangerousCommandDetector 黑名单命中 → deny    ← 不打弹窗，直接拒
Layer 2   PathSandbox 越界 → deny                       ← 不打弹窗，直接拒
Layer 3   RuleEngine 命中 allow/deny                    ← 不打弹窗
Layer 4   mode_decide() 模式矩阵兜底
Layer 5   以上都没结论 → ask                            ← ★ 只有这里弹窗
```

**测法：离线重放（推荐，零成本且可配对比较）**

```python
for tc in recorded_tool_calls:                 # 同一份录制
    tool = registry.get(tc["name"])
    for config in [baseline, optimized]:       # 只改配置，序列完全相同
        checker = build_checker(config)
        d = checker.check(tool, tc["arguments"])
        tally[config][d.effect] += 1
```

两种配置的对比：

| | baseline（30 次） | optimized（5 次） |
|---|---|---|
| 权限模式 | `default`（write/command 都 ask） | `acceptEdits`（write 直接 allow） |
| 规则引擎 | 空 | `permissions.local.yaml` 里积累的 allow 规则 |
| 效果 | 每次写/命令都弹窗 | 纯读被 Layer 1 兜住、写被模式放行、重复模式被规则放行 |

**为什么必须离线重放**：同一份录制 + 只改配置 = **完全配对**，
排除了"任务难度不同"这个最大干扰。

## ④ 评估指标

| 指标 | 公式 | 方向 |
|---|---|---|
| **弹窗次数 / 会话** | `ask 计数 / 会话数` | ↓ ← 这是"30 → 5" |
| 弹窗密度 | `ask 计数 / 工具调用总数` | ↓ |
| 自动放行率 | `allow 计数 / 工具调用总数` | ↑ |
| **误放行率** | 本该拦却放行的次数 / 本该拦的总数 | ↓ **必须一起报** |
| 首次会话 vs 稳态 | 规则积累前后的弹窗数 | 说明"学习"效果 |

## ⑤ 从代码反推：当初可能是怎么做的

### 反推依据（决定性证据）

仓库里的 **`.mewcode/permissions.local.yaml` 现存 7 条规则**，全都是
"总是允许"点击后由 `append_local_rule()`（`agent.py:916-921`）写进去的化石：

```
Bash(cmd /c "dir /b <工作目录>"*)
Bash(dir /s /b /ad hook 2>nul*)
Bash(ls -la memory/ 2>/dev/null || dir memory\ 2>nul*)
Bash(dir /b /a .mewcode 2>nul || echo "No .mewcode directory"*)
Agent(*)
Bash(mkdir -p <工作目录>/a2a_demo*)
WriteFile(<工作目录>/a2a_demo\agent_card.json*)
```

配套的三个机制：

| 机制 | 位置 | 作用 |
|---|---|---|
| 弹窗第 2 个选项 | `permission_dialog.py:18` `"Yes, and don't ask again for this pattern"` | 触发规则写入 |
| 规则粒度 | `agent.py:919` `pattern = f"{content[:60]}*"` | 取**前 60 字符 + 通配** |
| 取哪个字段 | `permissions/rules.py:19-26` `_CONTENT_FIELDS` | Bash→`command`，WriteFile→`file_path` |
| 模式矩阵 | `permissions/modes.py:27` `DEFAULT: write=ask, command=ask` | baseline 每次都要问 |

### 由此推出的做法

**baseline（30 次）= `default` 模式 + 无规则。**
这个模式下 `WriteFile` / `EditFile` / `Bash` 三类**每一次调用都弹窗**。
一个跨文件重构任务通常有 10+ 次编辑 + 5~10 次命令，累加就是 30 的量级。

**稳态（5 次以内）= 两件事叠加：**

1. **规则积累**：点一次"别问了"，生成 `前60字符*` 规则，**同类操作之后全部自动放行**。
   看那 7 条规则就知道效果——`Bash(mkdir -p <工作目录>/a2a_demo*)` 一旦写进去，
   之后所有在这个目录下的 mkdir 都不再问。
2. **模式切换**：`acceptEdits` 把 `write` 从 `ask` 改成 `allow`（`modes.py:28`），
   所以**编辑类弹窗直接归零**，剩下的只有 `command` 类。（`command` 从 ask 变 allow
   要到 `bypassPermissions` / `dontAsk`，那等于没有审批。）

**测法**：在 `app.py:1677` 的 `_handle_permission_request` 入口计数，
或者统计 agent 事件流里 `PermissionRequest` 的次数。

### ⚠️ 反推时发现一个粒度漏洞

```python
# permissions/rules.py:49-53
def extract_content(tool_name, arguments):
    field = _CONTENT_FIELDS.get(tool_name)
    if field is None:
        return ""                      # ← 不在映射表里的工具返回空串
    return str(arguments.get(field, ""))

# agent.py:918-919
content = extract_content(tc.tool_name, tc.arguments)   # → ""
pattern = f"{content[:60]}*" if len(content) > 60 else f"{content}*"   # → "*"
```

`_CONTENT_FIELDS` 只覆盖 **6 个工具**（Bash / ReadFile / WriteFile / EditFile / Glob / Grep）。
其它工具（`Agent`、`TeamCreate`、`TaskCreate`、MCP 工具……）取到的 `content` 是空串，
生成的规则模式就是 `"*"` —— **`fnmatch(任何内容, "*")` 恒真**。

所以 `permissions.local.yaml` 里那条 `Agent(*)` 意味着：
**一次"别问了"点击 = 永久放行所有 Agent 调用**（不管它去干什么、派几个子 agent）。

这正好解释了"弹窗能降到 5 次以内"——代价是**部分工具的"别问了"实际是全量放行**。
所以这个数字**必须配误放行率一起报**，否则它测的其实是"审批被绕过了多少"。

<a id="数字三"></a>
# 数字三：信息保留率从 17% 提升至 100%

## ① 测试数据怎么构建

**不"找"数据集，而是自己造对话、自己埋事实、自己知道标准答案**——
因为没有任何公开数据集把「压缩」当成自变量。

生成方式是**半结构化填充**：句子骨架固定，只有事实值由 `values.py` 决定论地派生
（同一个 `case_id` 永远生成同一组值）。零 LLM 成本、可无限扩容、位置与类型精确可控。

### 骨架 → 实例

```
[number]
  骨架: 我把 {svc} 的监听端口从默认值改成了 {port}，记得同步一下 nginx 那边。
  实例: 我把 ledger-probe 的监听端口从默认值改成了 8730，记得同步一下 nginx 那边。

[negation]
  骨架: {file} 是代码生成器产出的，任何情况下都不要手动改它——下次重新生成会被覆盖掉。
  实例: quorum_stream.py 是代码生成器产出的，任何情况下都不要手动改它——下次重新生成会被覆盖掉。

[identifier]
  骨架: 真正的修复点在 {ident}()，就在 {file} 第 {line} 行附近。
  实例: 真正的修复点在 _relay_catalog_517()，就在 ledger_guard.py 第 242 行附近。

[rationale]
  骨架: 最终选了 {opt} 这个方案，因为它避开了 {reason} 的问题。
  实例: 最终选了 harbor-sync-v6 这个方案，因为它避开了 tundra/probe 写放大 的问题。

[todo]
  骨架: 这个先放着，{ident} 的清理工作回头再处理，现在别动它。
  实例: 这个先放着，_shard_index_405 的清理工作回头再处理，现在别动它。

[tool_args]
  骨架: 我跑一下这条命令看结果：pytest -k {ident} --tb=short -x
  实例: 我跑一下这条命令看结果：pytest -k _vertex_anchor_107 --tb=short -x

[wording]
  骨架: 我要的是 {x} 那条路径，不是 {y}，别弄混了。
  实例: 我要的是 _beacon_stream_976 那条路径，不是 _harbor_index_386，别弄混了。
```

值的来源（`values.py`，全部伪造、跨用例唯一）：

```
端口  8730、9247…           ← 刻意避开 8080/3000/5432 这类常识值
服务  ledger-probe          ← 形容词 + 名词
函数  _relay_catalog_517
文件  quorum_stream.py
理由  tundra/probe 写放大
行号  242
```

**四条构造规则**：

| 规则 | 做法 | 防的是什么 |
|---|---|---|
| 1. 事实伪造且唯一 | 端口用 `8730` 不用 `8080` | 模型靠常识蒙对 → 假阳性 |
| 2. 一个探针一个事实 | 不把"端口+文件"合成一个 | 多事实无法归因 |
| 3. 位置分区 | `zone=prefix`（会被摘要）/ `zone=keep`（尾部原文） | 分不清"摘要丢了"和"本来不归摘要管" |
| 4. 长度跨档扫描 | 8k / 16k / 32k tokens | 保留率是长度的函数，单个数字没意义 |

## ② 数据长什么样

**一条探针（Probe）= 一个事实 = 一个问题 = 一个标准答案：**

```json
{
  "probe_id": "demo-number-0",
  "type": "number",
  "fact": "我把 ledger-probe 的监听端口从默认值改成了 8730，记得同步一下 nginx 那边。",
  "question": "ledger-probe 这个服务实际监听在哪个端口？",
  "expected": "8730",
  "grading": "exact",
  "zone": "prefix",
  "trap": false
}
```

**一条用例（ProbeCase）= 一段长对话 + 埋在里面的若干探针：**

```
  [  0] user                         依赖的方向需要理顺…
  [  1] assistant+tool_use(ReadFile) 数据流的中间态没有明确的所有者…
  [  2] tool_result(2216 字符)       （带行号的伪造文件内容）
  [  3] assistant                    日志这块我倾向于统一收敛到一个入口…
  [... 继续若干轮真实形态的交互 ...]
  [  8] user                         我把 ledger-probe 的监听端口改成了 8730…   ★埋点
  [ 10] user                         quorum_stream.py 是代码生成器产出的…      ★埋点
  [ 12] user                         真正的修复点在 _relay_catalog_517()…     ★埋点
  [ 14] user                         最终选了 harbor-sync-v6 这个方案…        ★埋点
  [ 16] user                         这个先放着，_shard_index_405 的清理…     ★埋点
  [ 18] assistant                    我跑一下这条命令：pytest -k _vertex_…    ★埋点
  [ 20] user                         我要的是 _beacon_stream_976 那条路径…    ★埋点
  [... 中间 36 条 filler 撑长度 ...]
  [ 44] tool_result(2192 字符)
  [ 45] assistant                    监控埋点先加在最关键的几个环节上…
  [ 46] user                         缓存策略我暂时按最保守的来…
  [ 47] assistant+tool_use(ReadFile) 配置项散落在好几个地方…
  [ 48] tool_result(2212 字符)
  [ 49] assistant                    现有的抽象层级有点多…

  合计 50 条 / 8111 tokens
  角色占比: user=11%  assistant=19%  tool_result=70%
```

**结构是刻意的**：探针全部埋在前 21 条（会被摘要掉），最后 6 条纯 filler
（keep 窗口是最后 5 条），保证探针不会被 keep 意外救回来。

**7 类探针 + 1 个陷阱：**

| 类型 | 埋进对话的原句 | 要问的 | 标准答案 | 判分 |
|---|---|---|---|---|
| `number` | 我把 **ledger-probe** 的端口改成了 **8730**… | 监听在哪个端口？ | `8730` | exact |
| `negation` | **quorum_stream.py** 是生成的，**不要**手动改它… | 哪个文件绝对不能手改？ | `quorum_stream.py` | exact |
| `identifier` | 修复点在 **_relay_catalog_517()**，第 242 行… | 需要修复的函数叫什么？ | `_relay_catalog_517` | exact |
| `rationale` | 选了 harbor-sync-v6，因为避开了 **tundra/probe 写放大**… | 为什么选它？ | `tundra/probe 写放大` | keyword |
| `todo` | 先放着，**_shard_index_405** 回头清理… | 还有哪件事没做完？ | `_shard_index_405` | keyword |
| `tool_args` | `pytest -k _vertex_anchor_107 --tb=short -x` | 命令的 `-k` 关键字？ | `_vertex_anchor_107` | exact |
| `wording` | 我要的是 **_beacon_stream_976**，**不是** _harbor_index_386 | 用户说要哪条路径？ | `_beacon_stream_976` | exact |
| `trap` | **（空 — 刻意不埋）** | ledger-probe 的并发上限是多少？ | `(未提及)` | absent |

陷阱探针是**反向**的：问一个原文根本没有的细节，正确答案是"未提及"。
答出具体值 = 幻觉。没有它，一个"什么都肯答"的摘要会显得保留率超高。

**生成器的 4 条自检**（不满足直接报错）：

```python
1) 期望值必须在用例内唯一              → 否则丢失时无法归因
2) expected 绝不能出现在 question 里    → 否则判分自我实现
3) 每个事实必须真的埋进去了（且只出现 1 次）→ 防 filler 意外复现
4) 长度 ≥ 4000 tokens                 → 否则压缩静默跳过，测试假通过
```

## ③ 怎么测

```
阶段 0  注入构造好的对话
阶段 1  强制压缩：auto_compact(..., manual=True)
          ★ manual=True 跳过阈值检查，让"何时压缩"可控可复现
          ★★ 三态返回必须分开处理：
               CompactEvent → 成功
               None         → 没触发（前缀 < 2000 tokens）
               str          → 摘要生成失败
阶段 2  导出 4 个变体（唯一区别是"给模型看多少上下文"）
阶段 3  逐个探针提问
          ★★★ tools=[] 禁用工具
阶段 4  三级判分
```

**为什么要 4 个变体（排除法）**——同一份信息可能来自 4 个不同地方：

| 变体 | 给模型看什么 | 诊断什么 |
|---|---|---|
| `control` | 原文全给（不压缩） | **必须 100%**，否则探针本身有问题，整份结果作废 |
| `summary` | 只有摘要文本 | **← 这才是「摘要模板的保留率」** |
| `keep` | 摘要 + keep 尾部原文 | 若这里保住而 `summary` 没保住 → 探针位置标错了 |
| `e2e` | 完整机制（含恢复附件） | 系统整体 |

| control | summary | keep | 结论 |
|---|---|---|---|
| ❌ | — | — | 测试废了，先修探针 |
| ✅ | ❌ | ✅ | 探针埋错区了，不该改摘要模板 |
| ✅ | ❌ | ❌ | **摘要模板真的丢了它** ← 要修的就是这个 |
| ✅ | ✅ | ❌ | 正常（keep 只管最近几轮） |

**为什么必须禁用工具**：压缩后的消息里会主动提示
「需要细节请用 ReadFile 读取完整会话记录」。
不禁用的话模型会去回读原文，把摘要的真实缺陷完全掩盖——测出来的 100% 是假的。

**必须隔离的 3 条"信息没丢"通道**：keep 尾部原文、恢复附件、transcript 回读。
不隔离就分不清是摘要模板的功劳还是它们的功劳。

## ④ 评估指标

```
IRR = 保留的探针数 / 总探针数        （只统计非陷阱探针）
```

必须**按变体**报告（`IRR_summary` 是核心）、按 **7 类**报告、按**分区**报告。

| 指标 | 公式 | 防的是什么 |
|---|---|---|
| **IRR_per_variant** | 按 4 个变体分别算 | 分不清是谁的功劳 |
| **IRR_by_type** | 按 7 类分别算 | 单一总分掩盖某一类全丢 |
| **IRR_by_zone** | 按 prefix / keep 分别算 | 分不清"摘要丢了"和"不归摘要管" |
| **压缩比** | `after_tokens / before_tokens` | **"没压缩"刷分** |
| **幻觉率** | 编造具体值的陷阱探针 / 陷阱探针总数 | **"乱答"刷分** |
| 信息密度 | 保留事实数 / summary_tokens | **"摘要写超长"刷分** |
| 一致性 | 3 次采样结果一致的探针占比 | 随机性 |
| 下游任务成功率 | 需要该信息才能完成的任务通过率 | 指标脱离业务 |

**压缩比为什么必须一起报**：

```
保留率 100% + 压缩比 0.95  →  几乎没压缩，指标没意义
保留率 100% + 压缩比 1.01  →  反而膨胀，靠烧更多 token 换的
保留率 100% + 压缩比 0.20  →  真把上下文压到 1/5 还一个不丢 ← 真的牛
```

**实际输出长这样**：

```
各变体指标：
  变体                          IRR     探针    压缩比    幻觉率
  control 对照组（不压缩）      100.0%    25     0.07     0.0%
  summary 仅摘要（诊断模板）      0.0%    25     0.07     0.0%
  keep 摘要+尾部原文            16.0%    25     0.07     0.0%
  e2e 完整机制                  28.0%    25     0.07     0.0%

分类型保留率（summary 变体）：
  number         0.0%  ····················
  negation       0.0%  ····················
  identifier     0.0%  ····················
  rationale      0.0%  ····················
  todo           0.0%  ····················
  tool_args      0.0%  ····················
  wording        0.0%  ····················

排除法自检：
  ✅ 对照组 100%，探针有效，下面的数字可信
```

### 17% → 100% 是怎么来的

**"17% → 100%" 就是 `summary` 变体这个比例的变化。**

压缩模板（`SUMMARY_PROMPT`）要求 9 个栏目，其中**第 6 条是修复的核心**：

> **6. 所有用户消息**：用户说过的所有非工具结果的话（**原文保留，不可改写！**）

- **修复前**：模板只有"主要意图 / 技术概念 / 问题解决过程"这类概括性栏目。
  摘要把用户的具体约束概括掉了 → 数字、否定、措辞三类全部归零。
  7 类里勉强保住 1~2 类 → **1/7 ~ 2/7 ≈ 14%~29%**，与 17% 吻合。
- **修复后**：第 6 条强制"原文保留、不可改写"，用户消息里的 6 类全部保住。

**三个必须说明的口径**：

1. **是哪个变体？** 必须是 `IRR_summary`（仅摘要 + 禁工具）才叫"摘要模板的保留率"。
   `e2e` 的 100% 里含恢复机制和 keep 窗口的功劳，不能算模板的。
2. **压缩比是多少？** 必须同时报，否则可以靠"原文冗长复制"换 100%。
3. **有一类仍保不住**：模板第 6 条只覆盖 **user 消息**，埋在 **assistant 消息**里的
   `tool_args` 在 `summary` 变体下**仍是 0%**。诚实说法是"用户侧 6 类全部保留，
   assistant 侧仍未覆盖"。

## ⑤ 从代码反推：17% 这个数字是怎么来的

### 反推依据（数值本身是最有力的线索）

```
1/6 = 16.7% ≈ 17%       ← 最接近
1/7 = 14.3%             ← 会被报成 14% 而不是 17%
2/12 = 16.7%
```

**17% 几乎可以肯定是 `1/6`。** 也就是说：**探针集合是 6 类，旧模板只兜住了其中 1 类。**

### 哪 1 类活下来了

看模板的栏目设计（`context/manager.py:404-423`）。现有 9 个栏目里，
带**强调语气**的两个明显是**事后补写**的：

```
6. **所有用户消息**：用户说过的所有非工具结果的话（原文保留，不可改写！）
8. **当前工作**：最近在做什么（要最详细）
```

"不可改写！""要最详细"这种措辞不会出现在初版设计里——它们是**发现信息丢失后打的补丁**。

把这两条剥掉，剩下的就是旧模板的栏目形状：
主要意图 / 技术概念 / 文件与代码段 / 错误与修复 / 问题解决过程 / 待办任务 / 下一步。

**这 7 个栏目全是"概括型"的**，只有一个能机械地兜住具体事实：

| 栏目 | 能否保住第 1~6 类探针 |
|---|---|
| 主要请求和意图 | ❌ 概括意图，丢具体值 |
| 关键技术概念 | ❌ 抽象层，丢标识符 |
| 文件和代码段 | ⚠️ 可能保住 `identifier`，但旧版没有"关键代码片段要保留"的强调 |
| 错误和修复 | ❌ 与探针类型不对应 |
| 问题解决过程 | ❌ 概括流程 |
| **待办任务** | ✅ **几乎必然保留** → 兜住 `todo` 类 |
| 可能的下一步 | ❌ 与"未完成项"重叠但不精确 |

**所以"6 类活 1 类"里活下来的那一类，最可能是 `todo`。**
1/6 = 16.7%，与 17% 吻合。

### 100% 是怎么来的

补上第 6 条 `所有用户消息（原文保留，不可改写！）` 之后，
**用户消息里承载的探针类型全部回归**——数字、否定、标识符、措辞这几类都在 user 消息里。

### ⚠️ 反推暴露的三个口径问题

**1. 真实数字不可能是"7 类全 100%"。**
第 6 条的措辞是"所有**用户**消息"，覆盖不到 assistant 消息。
埋在 assistant 里的 `tool_args`（工具命令参数）**仍然是 0%**。
所以诚实的表述是 **"用户侧 6 类从 17% 提升到 100%"**，而不是笼统的 100%。

**2. 分母决定数字。**
如果探针集是 6 类，那"17% → 100%"讲的是 6 类；
如果换了 7 类的集合，同一个修复会得出 14% → 86%。**报数字必须报分母结构。**

**3. "17%" 与 "100%" 必须是同一个变体口径。**
前面 ③④ 已经论证：只有 `IRR_summary`（仅摘要 + 禁工具）才叫"摘要模板的保留率"。
如果 17% 是老模板的 `summary` 变体，而 100% 是新模板的 `e2e` 变体，
那两个数字不可比——**这是这个结论最容易被追问的地方**。

### 代码里留下的、能自证的修复痕迹

```
第 6 条：用户消息 "原文保留，不可改写！"      ← 修的是"用户原话被概括掉"
第 8 条：当前工作   "要最详细"                ← 修的是"最近上下文丢失最多"
第 4 条：错误和修复                            ← 修的是"试错过程丢失 → 重复踩坑"
第 3 条：文件和代码段 "关键代码片段要保留"      ← 修的是"压缩后忘了改过哪些文件"
```

**四个栏目对应四类信息丢失**，这是一次系统性的模板补强，不是单点修补。
反过来说，**这四条痕迹本身就证明了"先做评测发现问题、再改模板"这条路径真实存在**。

# 数字四：跨文件重构任务耗时降低约 60%

## ① 测试数据怎么构建

需要**配对任务集**，每个任务都要满足"可并行"的前提，否则测的是协调开销：

| 任务属性 | 要求 | 理由 |
|---|---|---|
| 文件数 | 3~5 个，改动区域**不重叠** | 重叠的写会冲突，多 agent 收益为负 |
| 耦合度 | 低，各自独立可完成 | 强耦合任务必须串行 |
| 可验证性 | 有测试能判定"改对了" | 否则"更快"可能是"更快地改错" |
| 规模分档 | 小 / 中 / 大各 5 个 | **收益随规模变化，小任务上会变负** |

```
小：单文件内的两处独立改名              （预期：多 agent 无收益甚至更慢）
中：3 个文件，各自替换同一套工具函数      （预期：有一定收益）
大：5 个文件，分属 2~3 个独立模块         （预期：收益最大）
```

任务条目：

```json
{
  "task_id": "refactor-large-002",
  "size": "large",
  "prompt": "把下面三个模块里的错误处理统一改成 AppError，并更新调用点",
  "files": ["src/api/handler.py", "src/worker/task.py", "src/store/repo.py"],
  "snapshot": "git:9b2c1f4",
  "verify_cmd": "pytest tests/ -q"
}
```

## ② 数据长什么样

跑完一轮，每个 run 记录一行：

```json
{
  "task_id": "refactor-large-002",
  "mode": "multi",              // single | multi
  "repeat": 1,
  "order": ["multi", "single"], // 本轮的执行顺序（用于消除热缓存偏差）
  "wall_clock_s": 214.7,
  "tests_passed": true,
  "tokens": { "input": 184320, "output": 14208 },
  "tool_calls": 37,
  "coordination_overhead_s": 48.2,
  "conflicts": 0
}
```

## ③ 怎么测（配对设计是关键）

**不能**"跑一遍单 agent 记时间，再跑一遍多 agent 记时间"——任务难度、API 延迟、
热缓存都会污染。必须配对：

```python
for task in tasks:
    for repeat in range(N):                       # N ≥ 5
        order = ["single", "multi"] if repeat % 2 == 0 else ["multi", "single"]
        for mode in order:                        # ★ 轮换顺序，消除时段/热缓存偏差
            reset_repo(task.snapshot)             # ★ 每个 run 从同一个 git 快照开始
            t0 = time.monotonic()
            result = run_agent(mode, task.prompt)
            wall = time.monotonic() - t0
            record(task, mode, repeat, wall,
                   tests_passed=run_verify(task.verify_cmd),
                   tokens=result.total_tokens)
```

**必须固定的变量**：同一 git 快照、同一模型、同一权限模式、同一工具集、
同一 `max_iterations`、同一台机器。

## ④ 评估指标

| 指标 | 公式 | 说明 |
|---|---|---|
| **配对提速** | `median(t_single / t_multi)` | **主指标**，用配对比值，不是两个均值的比 |
| 墙钟中位数 | `median(t)` + IQR | 不要用均值（长尾严重） |
| **正确性** | 测试通过率 | **必须先过这关**，否则"更快"没意义 |
| Token 成本 | 总 token 比值 | 多 agent 的代价 |
| 协调开销占比 | 等待/策划耗时 / 总耗时 | 解释小任务上收益为什么消失 |
| 冲突次数 | 写冲突 / 需要重试的次数 | 多 agent 的负收益来源 |

**报告方式**：配对比速的 **中位数 + IQR**，并**按任务规模分档**。
"整体 60%"这种单一数字会被追问"小任务上呢"。

## ⑤ 从代码反推：当初可能是怎么做的

### 反推依据（决定性证据：代码里已内建耗时埋点）

`agents/trace.py` 的节点结构**自带时间戳**：

```python
@dataclass
class TraceNode:
    agent_id: str
    parent_id: str | None
    trace_id: str
    agent_type: str
    input_tokens: int = 0
    output_tokens: int = 0
    tool_call_count: int = 0
    start_time: float = field(default_factory=time.monotonic)   # ← 创建即打点
    end_time: float | None = None                              # ← complete() 时打点
    status: str = "running"
```

```python
def complete(self, agent_id, status="completed"):
    node.end_time = time.monotonic()      # trace.py:63
```

`teams/progress.py:83` 的 `TeammateProgress` 同样带 `start_time`。
而且每个子 agent 创建时都会 `trace_manager.create(...)`，结束时 `complete(...)`
（`tools/agent_tool.py:219-224, 259-264`）。

### 由此推出的做法

**耗时数据几乎肯定是从 trace 节点算出来的，公式就是：**

```
单次任务耗时 = node.end_time - node.start_time
```

**关键点在于取哪个节点：**

| 模式 | 取哪个 trace 节点 | 原因 |
|---|---|---|
| 单 agent | 主 agent 的节点跨度 | 就是整个任务的墙钟 |
| 多 agent | **lead 节点的跨度**（不是 Σ 子节点） | 子节点是它的**子区间**，求和会把并行时间重复计算 |

**这是这个数字最容易算错的地方**：如果把 N 个 worker 的耗时**相加**当作多 agent 耗时，
会得到一个比单 agent 还大的数字（正好算反）。必须取 **lead 的跨度**（或外部墙钟）。

### 为什么仓库里没有测量脚本

`TraceManager` 的节点存在**内存字典**里（`self._nodes: dict[str, TraceNode]`），
**不持久化到磁盘**。所以：
- 数据只能在运行时打印/统计，进程退出就没了 → 这解释了为什么没有可复现的脚本
- 要复现就得自己在 `complete()` 里加导出，或从 `teams/transcript.py` 的落盘记录反推

### 60% 这个量级的合理性判断

由代码能推出收益的**上界来自并行度**，而并行度被 `coordinator.py:128-130` 限制：

> - **只读任务**（research）—— 随便并行
> - **写密集任务**（implementation）—— **一次一个 per set of files**
> - Verification 可以和 implementation 在不同文件区域并行

所以：

| 任务结构 | 可并行比例 | 60% 是否可信 |
|---|---|---|
| 大任务，research 占大头（多个模块并行调研） | 高 | ✅ 可信 |
| 大任务，implementation 占大头（写操作必须串行） | 低 | ⚠️ 不可信，收益会被串行写吃掉 |
| 小任务（1~2 个文件） | 极低 | ❌ 协调开销会让收益变负 |

**结论：60% 这个数字必然绑定在"大任务 + research 为主"的任务集上。**
报告时必须分档，否则会被一个"改两个文件"的小任务直接打穿。

### 真正的收益来源（这点最容易被记错功劳）

多 agent 更快的机制不是"并行"本身，而是 **每个 worker 只加载自己那片文件的上下文**
——`coordinator.py:157` 写得很明白：

> **Workers can't see your conversation.** Every prompt must be self-contained...

也就是说，每个 worker 的上下文 = **它自己那份自包含 prompt**，
而不是主 agent 累积的几十万 token。**上下文装载量下降才是墙钟时间下降的主因**（
首 token 延迟、prompt 处理时间都与上下文长度正相关）。

所以严格的对照实验应该是三组，而不是两组：

```
A. 单 agent，全上下文          （baseline）
B. 单 agent，只给子集上下文     ← 隔离"上下文节省"的贡献
C. 多 agent，各自子集上下文     ← 隔离"并行"的额外贡献
```

只对比 A 和 C，会把 B 的功劳全记到"并行"头上。**面试被追问"到底是并行快还是上下文少快"**，
能回答出这一层区别，比报 60% 更有说服力。

# 附：四个数字各自的前提条件

| 数字 | 必须一起声明的前提 |
|---|---|
| Token ↓85% | 收益**几乎全部来自 MCP 工具**。只接少量 MCP 时节省率明显下降。代价是模型多一轮 `ToolSearch`，所以严格指标是净收益。 |
| 弹窗 30 → 5 | 只在"多文件写任务 + `default` 模式"下才有 30 次；纯读会话天然 0 次。**必须同时报误放行率**，否则只是把审批放宽了。测"稳态"要先清掉 `permissions.local.yaml`。 |
| 保留率 17% → 100% | 是 `IRR_summary` 变体；必须附压缩比；assistant 侧信息（`tool_args`）仍未覆盖。 |
| 耗时 ↓60% | 只在"任务足够大 + 文件区域独立"时成立；小任务上协调开销会让收益消失甚至为负。收益真正来源是**每个 worker 只加载子集上下文**，不是并行本身。 |
