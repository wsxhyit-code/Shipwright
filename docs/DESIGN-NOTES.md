# 设计取舍与踩坑记录

这些是"当时有两条路，为什么选了这条"的记录。放在这里而不是 README，
是因为它们属于**过程**；README 讲的是**结果**。

---

## 1. 为什么允许 agent 自己推送（一次设计更正）

最早的设计是「AI 只产出补丁、**永不推送**」，靠一个 hook 拦 `git push`。实测那个 hook：

| 命令 | 结果 |
|---|---|
| `git push` / `git push -u origin main` / `git  push` | 拦住 |
| `bash -c "git push"` / `cd x && git push` / `/usr/bin/git push` | 拦住 |
| **`git -C . push`** | **放行 ← 绕过** |
| **`git -c core.pager=cat push`** | **放行 ← 绕过** |
| **`python -c "subprocess.run(['git','push'])"`** | **放行 ← 绕过** |
| **`git\ push`**（反斜杠转义空格） | **放行 ← 绕过** |
| **`$(which git) push`** | **放行 ← 绕过** |

**5 / 9 种写法能绕过**，而 `git -C <目录> push` 恰恰是 agent 最常用的写法 ——
所以"AI 永不推送"实际是一个**可绕过的正则**，不是保证。

与其用它假装拦住，不如明确允许推送，把真正承重的三条守住
（只推 `agent/*`、绝不合并、验证先于推送）。**把"AI 只能产出补丁"当成铁律，
是把实现手段当成了目的。**

## 2. 为什么门禁只信"退出码"

命令验证这一层只有一种信号：**被验证命令的退出码**。模型无法伪造它。

所以 `CreatePR` 的顺序是硬编码的：

```
规范检查 → 命令验证（退出码）→ 独立验证 → 提交 → 推送 → 开 PR
```

任何"先推再说"的实现都会让门禁失去意义 —— 推上去的分支即使 PR 没开成，
代码也已经到远端了。

## 3. 为什么独立验证者拿不到写权限和 Bash

它的独立性靠**机械保证**而不是提示词：

| 维度 | 保证方式 |
|---|---|
| 上下文独立 | 全新 `ConversationManager()`，看不到实现对话 |
| 工具只读 | 注册表里只放 `ReadFile` / `Grep` / `Glob`，`WriteFile` / `Bash` / `CreatePR` 不存在 |
| 权限兜底 | 再加 `PermissionMode.PLAN`，即使注册表被绕过也写不了 |
| 结论必须显式 | 必须输出 `VERDICT: PASS` / `VERDICT: FAIL` |
| 没结论 = 不通过 | 解析不到就按 FAIL（fail-closed） |

它拿到的提示词要求的是**找茬**而不是**确认** —— 只要求"确认对不对"时，
模型倾向于给你想要的答案。

**代价**（值得明确知道）：它因此只能做**静态推理** —— "我追了调用链，逻辑成立"，
而不是"我跑过，绿了"。这两件事的价值差很远。如果要给它执行能力，
应该给**只读命令**（跑测试、看 diff），而不是放开成完整 shell。

## 4. 为什么"没接入的能力"要报错，而不是返回空

没接部署数据源时，调用 `ListDeploys` 会抛 `OpsCapabilityMissing`，**不返回空列表**。

理由：返回空会让模型把"**没接入**"读成"**没有异常**"，然后非常自信地得出错误结论 ——
这比直接报错危险得多。`describe()` 会把能力清单（`✓ 告警 / ✗ 部署`）交给模型，
让它在排查**开始前**就知道哪些数据源不可用。

同一条原则的其他落点：

| 场景 | 做法 |
|---|---|
| `enabled: true` 却没写 `verify_command` | **启动就报错** —— 没有验证命令的 CreatePR 等于把铁律拆了，而它看起来还在工作 |
| `token_env` 声明的环境变量读不到 | **启动就报错** —— 否则会静默发出无认证请求拿到 401，而 401 很容易被误读成"服务端权限配错了" |
| `mode: pr` 但既没有 `gh` 也没有 token | **启动就报错** —— 不这么做，agent 会改完代码、两层验证都过、分支都推上去之后才发现开不了 PR |
| `kind` / `capability` 拼错、同一能力配两个后端 | 报错。这份配置只在**真出事时**才被用到，那时才发现"配置根本没生效"，代价是一次故障排查 |

**静默降级比启动失败危险得多。**

## 5. 打包：为什么 `pyproject.toml` 刻意不用 `packages.find`

这个仓库是"源码根 = 包根"的扁平布局（`__init__.py` 在仓库根），靠
`package-dir = {"mewcode": "."}` 映射成可安装的包。

第一次是用 `packages.find` 写的，坏了：`find` 会覆盖 `package-dir` 映射，
在仓库根扫出来的"顶层包"是 `agents` / `tools` / `hooks` 这些，而不是 `mewcode.*` ——
于是打出来的 wheel 里文件直接躺在 `site-packages` 根目录，**`import mewcode` 根本不存在**，
console_scripts 入口也是死的。它还会把 `build/` 当成包打进去（实测那个 wheel 有
256 个文件来自 `build/`）。

所以包清单是**显式列出**的。

## 6. 沙箱：为什么是"不给"而不是"禁止"

| # | 铁律 | 不做会怎样 |
|---|---|---|
| ① | 绝不挂 `docker.sock` | agent 能 `docker run --privileged -v /:/host` 拿到宿主 root。**这是业界最常见的沙箱穿透** |
| ② | 绝不挂宿主 `$HOME` / `.ssh` / 云凭证 | 只挂 `/work`（代码）和 `/artifacts`（产物） |
| ③ | 默认禁出网 | 否则 agent 能把代码发出去、也能拉任意代码进来 |

**"起测试环境"分三层，只有两层该给 agent**：

| 层 | 例子 | 谁做 | 为什么 |
|---|---|---|---|
| 依赖服务 | PostgreSQL / Redis / mock | 平台预先起好 | 起容器要 docker 权限 → 给了就破沙箱 |
| 项目依赖 | `pip install -r requirements.txt` | ✅ agent | 每个项目不同，且随代码变 |
| 测试数据 | `alembic upgrade head` | ✅ agent | 跟着数据模型走 |

## 7. 一个反复出现的教训：断言"声明"不等于断言"效果"

`docker/compose.test.yml` 原来声明了 `test-net: {internal: true}`，
但**三个服务都没有 `networks:` 字段** —— compose 于是把它们放到了自动创建的
`..._default` 网络上，那个网络 **`internal=false`**。实测结果：

| 项 | 应有 | 实际 |
|---|---|---|
| 服务所在网络 | `test-net`（internal） | `..._default` |
| 网络 internal 标志 | `true` | **`false`** |
| 容器能否连公网 | 不能 | **能连上 `1.1.1.1:443`** |

**铁律③完全失效，而当时的 `test_docker_config.py` 照样全绿** ——
因为那条测试只做文本正则：文件里有 `internal: true` 就判定成立。
它断言的是**声明**，不是**效果**。

修法：① 每个服务显式写 `networks: [test-net]`；② 换成**结构化**测试
（用 YAML 解析后检查每个服务确实加入了那个 internal 网络）；③ 再加一条
"网络全名和 `run-agent.sh` 默认值一致"的测试（名字对不上时脚本会直接 `network not found`）。

同一个毛病在别处也出现过，处理方式都一样：

| 同类问题 | 处理 |
|---|---|
| 沙箱自检里 `test -d /root` 是**恒真断言**（基础镜像自带 `/root`），永远 FAIL | 改成 `test -r /root` + 一条"`HOME` 下没有 ssh 私钥" |
| 推送相关断言在沙箱里**空过**（`git push` 跑不起来 → 无法区分"没推"和"推失败了"） | 加**控制组**先证明本环境真能 push；做不到就如实 skip 并打出原因，而不是假装通过 |
| `git apply` 打不上补丁时**退出码仍是 0**（只打印 `Skipped`） | 不信任退出码：自己按 unified diff 应用，或用 blob 哈希对账 |
