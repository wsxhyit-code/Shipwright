# 线上故障定位

## 排查顺序（不要跳步，也不要乱序）

前面的步骤会给后面的步骤提供线索。跳过任何一步，你都会在最后一步猜。

### ① 看有哪些告警

```
ListAlerts(severity="critical")
```

先确定**影响面**：涉及几个服务、几个区域、什么环境（prod / staging）。

### ② 看最严重那条的详情

```
GetAlert(alert_id)
```

拿到服务名、环境、区域。**接下来的所有查询都以这个服务为中心。**

### ③ 查日志聚类，找到主要错误

```
QueryLogs(service="<服务名>", window="15m", level="ERROR")
```

看两件事：

- **哪个聚类占绝对多数**（通常是根因，其余是它的连带效应）
- **首次出现时间**（后面要和部署时间对比）

需要看完整堆栈时：

```
GetLogSample(cluster_id="<上一步返回的聚类 ID>", count=5)
```

⚠️ **聚类 ID 要用 `QueryLogs` 返回值里的那个，别自己拼 `C-1` 这种序号。**
真实后端（`LokiLogBackend`）的 ID 是从**日志签名**算出来的（形如 `C-a23ff9`），
同一个错误在不同时间窗口里 ID 相同，可以直接跨查询对照；
用错 ID 会直接报「不在最近一次结果里」，而不是静默返回另一类错误的日志。

⚠️ **不要跳过聚类直接拉原始日志** —— 那是把几万行日志塞进上下文，得不偿失。

### ④ 查指标，**重点看分组之间的差异** ⭐

```
QueryMetrics(metric="http_5xx_rate", window="30m", group_by="pod")
```

这一步是**整个排查的分水岭**：

| 观察结果 | 指向 |
|---|---|
| **只有某一个实例异常** | 问题在那个实例上 → 查它的最近部署（→ ⑤） |
| **所有实例都异常** | 问题在依赖服务 / 配置 / 流量上 → 换方向查 |
| **指标无异常但告警响了** | 可能是误报，或者问题在告警覆盖不到的地方 |

**只看总量平均值会错过关键线索** —— 平均下来可能完全正常，但有一个实例已经全挂了。

### ⑤ 查部署，和错误起始时间对比 ⭐

```
ListDeploys(service="<服务名>", limit=5)
```

**如果错误开始时间和某次部署接近（几分钟到十几分钟），基本可以锁定是这次发布引入的。**

拿到 `commit` —— 这是进入代码层面的钥匙。

### ⑥ 把时间线对齐

```
BuildTimeline(service="<服务名>", window="30m")
```

这个工具只把事实按时间摆好，**不下结论**。你来看：

```
10:11  [部署] v2.14.3 → pod-3
10:23  [日志首现] NullPointerException at OrderService.getTier:142
10:25  [指标拐点] http_5xx_rate@pod-3 0.1 → 8.4
10:38  [告警] critical HTTP 5xx rate high
```

**部署在 10:11，错误在 10:23 首次出现，只有 pod-3** —— 因果链已经很清楚了。

### ⑦ 读代码，定位到具体位置 ⭐⭐

**这一步是普通运维 AI 做不到的 —— 它只能告诉你"pod-3 有问题"，而你能告诉人"是 142 行少了判空"。**

```
# 从日志聚类里拿到 "OrderService.getTier(OrderService.java:142)"
Grep(pattern="getTier", path=".")
ReadFile(file_path=".../OrderService.java", offset=130, limit=30)
```

到了代码层面要回答三个问题：

1. **这行代码在本次发布的 diff 里吗？** 如果在，基本可以定案
2. **为什么只有这个实例出问题？** 是灰度发布（只有 pod-3 更新了），还是数据差异
3. **有没有同类问题只修了一处？** 这是最常见的"改了一半"

如果工作区里有这个仓库，还可以：

```
Grep(pattern="getProfile\\(\\)\\.get", path=".")   # 找出所有同类调用点
```

### ⑧ 建故障工单

```
CreateIncident(
    service="orders-api",
    title="orders-api 5xx 突增（pod-3）",
    severity="critical",
    root_cause="v2.14.3 删掉了 OrderService.getTier 里对 getProfile() 的判空",
    evidence="""
      日志：聚类 C-1，NullPointerException at OrderService.java:142，1,204 条，
            首次 10:23:41
      指标：http_5xx_rate 仅 pod-3 从 0.1% 升至 12.3%；其余实例平稳
      部署：D-5521 v2.14.3 于 10:11 发布到 pod-3，commit 9b2c1f4
      代码：OrderService.java:142 `return user.getProfile().getTier()` 缺判空，
            该行在 commit 9b2c1f4 中被改动
    """,
)
```

**系统会拒绝没有证据链的工单。** 证据必须具体到：日志聚类 ID、指标数据、部署版本、文件行号。

## 反面模式（这些做法会被判定为失败）

| ❌ | 为什么不行 |
|---|---|
| **查一次日志就下结论** | 日志里的错误常常是连带效应，不是根因 |
| **只看指标总量，不看分组** | 平均值会把"一个实例全挂"平均掉 |
| **不查部署，直接猜是代码问题** | 时间对不上就不是这次发布引入的，猜了也白猜 |
| **停在"建议重启服务"** | 重启只是止血，没有回答"为什么会这样"。**必须定位到代码** |
| **把日志全文贴进报告** | 报告要的是证据链的精炼引用，不是日志搬运 |
| **证据缺失时编造一个根因** | 系统会拒绝，而且这会误导后续的修复 |

## 输出格式

给用户的结论要按这个顺序：

```
## 结论
<一句话根因>

## 证据链
- 日志：<聚类 ID + 签名 + 条数 + 首次时间>
- 指标：<指标名 + 哪个分组 + 变化幅度>
- 部署：<版本 + 时间 + 目标实例 + commit>
- 代码：<文件:行号 + 这行在本次改动里吗>

## 影响面
<哪些实例 / 哪些接口 / 多少请求受影响>

## 建议
<修复方向；如果需要改代码，说明改哪里>
```

**证据链是核心**：每个结论后面都要能跟上具体出处。没有出处的结论不要写。
